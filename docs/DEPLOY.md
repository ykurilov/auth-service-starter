# Развёртывание и обслуживание

Основной путь установки - Docker Compose на Linux VPS. Сначала заполните `.env` по README. Ключи и БД принадлежат вашей установке; внешние адреса в примерах заменяются вашими.

## HTTPS через nginx

Установите Docker Engine с Compose v2 по [официальной инструкции Docker](https://docs.docker.com/engine/install/ubuntu/) и nginx средствами своей системы. Направьте DNS-запись `auth.example.com` на VPS. В шаблоне `deploy/nginx/auth-v3.conf` замените домен и при необходимости порт, затем подключите файл:

```sh
sudo cp deploy/nginx/auth-v3.conf /etc/nginx/sites-available/auth.conf
sudo ln -s /etc/nginx/sites-available/auth.conf /etc/nginx/sites-enabled/auth.conf
sudo nginx -t
sudo systemctl reload nginx
```

Для TLS установите certbot по [инструкции для своей ОС](https://certbot.eff.org/instructions), затем:

```sh
sudo certbot --nginx -d auth.example.com
```

Включите предложенный редирект HTTP -> HTTPS. В `.env` должны быть `PUBLIC_ISSUER_URL=https://auth.example.com` и `SSO_COOKIE_SECURE=true`. Проверка:

```sh
curl --fail https://auth.example.com/live
curl --fail https://auth.example.com/.well-known/openid-configuration
```

`issuer` и адреса discovery должны указывать на ваш публичный HTTPS-домен. Вход начинается из подключённого приложения, а не с корня сервиса.

## Доверенные прокси и порты

Приложение в compose опубликовано только на `127.0.0.1:${HOST_PORT:-3016}`. PostgreSQL и Redis наружу не опубликованы. Настройка `PORT` внутри compose закреплена на 3016; для изменения внешнего порта используется HOST_PORT.

nginx на хосте приходит в контейнер с адреса Docker gateway. По умолчанию выделена сеть `172.30.240.0/24`, gateway `172.30.240.1`; `TRUST_PROXY=loopback,172.30.240.1`. Если эта подсеть занята, измените DOCKER_SUBNET/DOCKER_GATEWAY и соответствующий адрес в TRUST_PROXY. При пересоздании сети предварительно остановите compose без удаления volumes. Подсеть и `TRUST_PROXY` задайте до первого `docker compose up`: если проверка по README и входы работают, но все пользователи выглядят как один IP, причина обычно здесь.

Ошибка `Pool overlaps with other one on this address space` означает конфликт с существующей Docker-сетью. После проверки `docker network inspect` выберите свободную приватную подсеть и согласованно измените три строки `.env`, например:

```dotenv
DOCKER_SUBNET=10.250.240.0/24
DOCKER_GATEWAY=10.250.240.1
TRUST_PROXY=loopback,10.250.240.1
```

Пример подходит, только если эта подсеть свободна в вашей сети.

Для другого прокси укажите его IP/CIDR. Старые true/числа в TRUST_PROXY поддерживаются только для loopback; они не означают доверие произвольному источнику. На новом Fastify числовой hop-count напрямую не передаётся. Не разрешайте доверие всем адресам, а клиентский X-Forwarded-For перезаписывайте на границе.

`ACCESS_TTL_SECONDS` (время жизни access-токена, по умолчанию 900) не может быть меньше 30 секунд: приложение обновляет токен не чаще раза в 15 секунд, и с меньшим значением токен истекал бы раньше, чем его успеют обновить. Сервис с меньшим значением не запустится.

Блокировку пользователей сервис не поддерживает: у пользователя один статус, «активен».

TOKEN_RATE_LIMIT задаёт широкий бюджет token endpoint за 15 минут на исходящий IP серверных приложений. По умолчанию 10000; рассчитывайте значение по своему числу активных сессий и количеству приложений. Лимиты отправки и проверки одноразовых кодов считаются отдельно.

### Лимиты писем с кодом

| Что считается | Предел | Окно |
|---|---|---|
| Письма с одного IP на все адреса: новые входы и повторные отправки | 100, задаётся `CODE_REQUEST_PER_IP_HOURLY` | 1 час |
| Новые входы с одного IP на один адрес | 5 | 15 минут |
| Новые входы на один адрес со всех IP и всех подключённых приложений: пауза между письмами | 1 | 60 секунд |
| Новые входы на один адрес со всех IP | 20 | 1 сутки |
| Повторные отправки внутри одного входа | 3 | пока жив код, 15 минут |
| Проверки кода в одном входе | 5 | пока жив код |
| Неверные коды с одного IP на все входы; верный код не считается | как у писем, задаётся `CODE_VERIFY_PER_IP_HOURLY` | 1 час |
| Входы через Google с одного IP | 60, задаётся `GOOGLE_SIGNIN_PER_IP_15MIN` | 15 минут |

Повторная отправка в уже начатом входе не тратит лимиты адреса. Поэтому посторонний, который занял лимит чужого адреса, не мешает владельцу дослать код в свой вход. На один адрес за сутки уходит не больше 80 писем: 20 входов по 4 письма. Слот повторной отправки занимается в базе до отправки письма, поэтому параллельные запросы не превышают 3 повтора.

Остаточный компромисс. Лимит адреса защищает ящик от бомбинга с разных IP, поэтому его может занять любой, кто знает адрес. Сразу после чужого запроса владелец ждёт до 60 секунд и видит время ожидания на форме входа. Повторная отправка формы из того же браузера (двойное нажатие, «Назад») паузы не ждёт: открывается экран кода уже начатой попытки, нового письма нет. Если посторонний за сутки израсходует все 20 новых входов (из-за паузы на это уходит не меньше 20 минут), новый вход в этот адрес закрыт до конца суточного окна. Начатый вход владельца при этом продолжается. Полностью убрать это может только проверка человека, например капча. Сервис её не ставит: она требует внешнего сервиса и усложняет вход всем.

Если почтовый провайдер окончательно отказал, письмо и попытка не засчитываются в лимиты. Если провайдер не ответил вовремя, письмо могло уйти. Тогда попытка остаётся, повторная отправка считается потраченной, а код из этого письма становится действующим; пользователь видит, что письмо может прийти. Каждый код записывается под номером своей повторной отправки: если ответы провайдера на две быстрые повторные отправки пришли не по порядку, действует код более поздней отправки.

Класс или офис за одним IP делят общий бюджет писем и неверных кодов. 100 писем в час хватает примерно на 50 человек, если каждый один раз просит код повторно. Верные коды бюджет проверок не тратят, а лимит неверных кодов по умолчанию равен лимиту писем. Поэтому для большой группы достаточно поднять `CODE_REQUEST_PER_IP_HOURLY`: например, для 150 человек поставьте 300. `CODE_VERIFY_PER_IP_HOURLY` задавайте, только если хотите отдельный предел ошибок. Если группа входит через Google, поднимите и `GOOGLE_SIGNIN_PER_IP_15MIN` до числа людей, которые входят за 15 минут.

Перебор кода в одном входе ограничен отдельно: 5 проверок на попытку, от этих настроек он не зависит.

При исчерпании лимита страница показывает, через сколько можно повторить. Это же время приходит в заголовке `Retry-After`.

## Приложения и локальные демо

Для приложения на отдельном hostname достаточно краткой регистрации:

```sh
docker compose exec app node scripts/client.mjs add https://app.example.com
```

Для двух демо на одном localhost нужны разные client id. Полная форма Admin API принимает `id`, `type`, `redirectUris`, `allowedProviders`, `postLogoutRedirectUris`. Токен берётся из ADMIN_API_TOKEN и передаётся только в Authorization: Bearer; не помещайте его в URL и не сохраняйте в репозитории.

Пример тела регистрации Next.js-демо:

```json
{"id":"nextjs-demo","type":"internal","redirectUris":["http://localhost:3005/api/auth/callback"],"allowedProviders":["email"],"postLogoutRedirectUris":["http://localhost:3005/"]}
```

Для Hono аналогично: `id=hono-vite-demo`, порт 3007. Эти id уже указаны в `.env.example` примеров. Можно также добавить оба объекта в CLIENTS_JSON перед первым запуском; CLIENTS_JSON применяется однократно при первом запуске новой БД. После этого добавление, изменение и удаление выполняются через Admin API или client.mjs, независимо от содержимого CLIENTS_JSON.

«Выйти» на любом приложении завершает вход во всех приложениях этого браузера. Другие браузеры и устройства пользователя он не трогает: там вход сохраняется. Сессия приложения продлевается refresh не дальше, чем через год после последнего захода браузера на страницы входа: потом пользователь войдёт заново. Так выход и смена аккаунта всегда достают сессии браузера, даже когда SSO-cookie (`SSO_TTL_SECONDS`) уже истекла. Подробности — в SECURITY.md.

Изменение клиента может разлогинить его пользователей. Смена `type` отзывает все сессии клиента и гасит ещё не обменянные коды входа: пользователям нужно войти заново. Удаление провайдера из `allowedProviders` отзывает сессии, открытые через этот провайдер. Удаление клиента гасит его коды и сессии; клиент, созданный заново с тем же id, считается новой регистрацией и старые коды не принимает. Изменение только адресов возврата сессии не трогает.

## Резервные копии

Дамп содержит персональные данные и ключи подписи. Храните его зашифрованным отдельно от VPS, ограничьте доступ и срок хранения. Не добавляйте его в GitHub.

```sh
mkdir -p backups
chmod 700 backups
(umask 077 && docker compose exec -T postgres pg_dump -U authv3 -d authv3 -Fc > backups/auth.dump.new) \
  && docker compose exec -T postgres pg_restore --list < backups/auth.dump.new > /dev/null \
  && mv backups/auth.dump.new backups/auth.dump \
  && echo "Резервная копия готова: backups/auth.dump" \
  || { rm -f backups/auth.dump.new; echo "Ошибка: резервная копия НЕ создана, прежняя копия сохранена" >&2; false; }
```

Новая копия сначала пишется во временный файл и проверяется. Прежняя копия заменяется только после успешной проверки, поэтому сбой не уничтожит её.

Проверяйте восстановление на отдельной БД. На новом сервере восстановите `.env` из защищённой копии и поднимите **только PostgreSQL**. Не запускайте app: при старте он заполняет новую БД миграциями и ключами. Команды ниже предназначены для пустого PostgreSQL volume новой установки:

```sh
docker compose up -d --wait postgres
docker compose exec -T postgres pg_restore -U authv3 -d authv3 --no-owner --single-transaction --exit-on-error < backups/auth.dump
docker compose up -d --build
```

Не выполняйте восстановление поверх работающей БД без плана переноса: существующие таблицы и активные сессии могут конфликтовать. Также сохраните `.env` в защищённом хранилище. Redis здесь сохраняет лимиты через AOF, но резервной копией пользователей остаётся PostgreSQL.

## Обновление

Перед обновлением сохраните дамп и прочитайте release notes о миграциях. В своей копии репозитория:

```sh
git pull --ff-only
docker compose up -d --build --wait
docker compose ps
curl --fail http://127.0.0.1:3016/live
```

Если вы меняли `HOST_PORT`, подставьте его вместо 3016. Миграции применяются при старте. Несколько копий сервиса над одной базой применяют их по очереди под общей блокировкой PostgreSQL, поэтому одновременный старт безопасен. Ожидание блокировки и сами миграции не ограничены таймаутами обычных запросов. **Не запускайте прежнюю и новую версии одновременно над одной базой.** Установка по README — одна копия сервиса, и `docker compose up -d --build` сначала останавливает прежний контейнер и только потом запускает новый, так что это правило выполняется само. Если вы держите несколько копий (свой оркестратор, балансировщик), обновляйте их с остановкой: сначала остановите все копии прежней версии, затем запустите новую. Совместная работа разных версий не поддерживается: прежняя версия не знает новых форматов токенов и привязок браузера, и часть пользователей может неожиданно выйти или не выйти. Обновление с миграцией `0018` (привязка браузера к цепочке SSO) никого не разлогинивает сразу. Браузер с живой SSO-cookie получит cookie привязки при следующем заходе на страницы входа. Если браузер не заходил туда, пока жила его SSO-cookie, сессии приложений, выданные в нём до обновления, продлеваются только до конца срока этой SSO-cookie, а затем пользователь войдёт заново. Обновление с миграцией `0019` (несколько привязок на цепочку) тоже никого не разлогинивает сразу: привязки переносятся в новую таблицу `sso_chain_bindings`. Старую таблицу удалит отдельная миграция, которая выйдет не раньше чем через год после `0019`: за этот срок истекают все привязки, записанные туда прежней версией. Перед обновлением на неё остановите все копии версий до `0019`: прежнюю версию останавливают, а не держат рядом с новой. До тех пор не удаляйте таблицу вручную. Обновление с миграцией `0020` (семейство refresh-токенов) тоже никого не разлогинивает: токены прежнего формата действуют, и первый же refresh выдаёт токен нового формата. Очистка теперь удаляет у живой сессии давно погашенные refresh-токены, поэтому история не растёт; повтор такого токена по-прежнему отзывает сессию. Обновление меняет и поведение выхода: «Выйти» больше не гасит сессии пользователя в других браузерах и на других устройствах, а смена аккаунта в браузере начинает новую цепочку SSO. Сессии приложений, выданные до миграции `0013`, не знают свой браузер, и их не достают ни «Выйти» по cookie привязки, ни смена аккаунта. Поэтому с `0019` refresh таких сессий больше не продлевает их срок: каждая доживает до срока, который был у неё на момент обновления (не больше `REFRESH_TTL_SECONDS`, по умолчанию 30 дней), а затем пользователь один раз входит в это приложение заново. Цена: у давних пользователей таких приложений через срок до 30 дней после обновления будет один повторный вход. Привязать такую сессию к браузеру задним числом нельзя: refresh присылает сервер приложения, а не браузер, и в данных нет надёжной связи с цепочкой. Возврат старого образа после изменения схемы может потребовать отдельной обратной миграции или восстановления дампа; автоматическое удаление данных не выполняется.

## Ключи подписи

Обычная ротация оставляет прежний public key для проверки ещё действующих JWT:

```sh
docker compose exec app npm run rotate-key
docker compose restart app
```

При утечке выполните ротацию, затем отзыв скомпрометированного retired kid:

```sh
docker compose exec app npm run rotate-key
docker compose exec app npm run revoke-key -- OLD_KID
docker compose restart app
```

`OLD_KID` — kid из строки `отправлены в retired: …`, которую печатает `rotate-key`. Если утёк ключ, ротированный раньше, найдите его kid в списке ключей: по дате создания или по полю `kid` в заголовке утёкшего JWT.

```sh
docker compose exec postgres psql -U authv3 -d authv3 -c "select kid, status, created_at, retired_at, revoked_at from signing_keys order by created_at"
```

Отозвать active key нельзя: сначала создаётся новый. Процесс загружает ключи при старте, поэтому перезапуск обязателен. Учтите кэш JWKS в подключённых приложениях и срок уже выданных access JWT. Команды выполняют готовые CLI из dist и не требуют TypeScript в контейнере.

## Локальная разработка без контейнера приложения

Используйте Node.js 22.12+. В `.env` задайте DATABASE_URL/REDIS_URL своих локальных сервисов; compose не публикует их порты. Для данных разработки используйте отдельную базу.

```sh
npm ci
npm run build
npm start
```

In-memory режим без DATABASE_URL предназначен только для тестов и разработки: пользователи и ключи в нём исчезают при перезапуске. Production требует PostgreSQL и настроенную почту.

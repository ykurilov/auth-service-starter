# Изменения безопасности перед первой публичной версией

Первая публичная версия подготовлена после четырёх независимых обзоров кода: двух Codex и двух Claude. Повторяющиеся сообщения объединены; предположения проверены отдельно. Репозиторий публикуется с новой историей, без конфигурации исходной установки, персональных данных и её ключей.

## Сессии и подключённые приложения

| Сценарий | Исправление |
| --- | --- |
| Пользователи одного сервера исчерпывают общий лимит token endpoint | Широкий настраиваемый предел по IP плюс отдельные бюджеты для проверенной сессии и пользователя/клиента. |
| Два процесса одновременно обновляют один refresh | Погашение и преемник записываются одной транзакцией; проигравший перечитывает результат. |
| Ответ с новым cookie приходит позже другого успешного ответа | В grace window возвращается тот же refresh-преемник, действующая голова повторно не погашается. |
| Временный 429/500 или сбой сети разлогинивает пользователя | Cookie сохраняется; ещё действующий access используется до истечения. После истечения защищённый маршрут отвечает 503. |
| `/me` и серверный `getUser` видят устаревшую сессию | `/me` обновляет самостоятельно; `getUser` отвергает истёкший access. |
| Next.js рендерит HTML со старым входящим cookie | Middleware передаёт изменённый Cookie в текущий серверный запрос. |
| Две вкладки используют одну попытку входа | У каждой попытки собственный запечатанный cookie с TTL. |
| Удалённое приложение продолжает получать токены | При выдаче проверяется действующий реестр и политика провайдера; связанные refresh-сессии отзываются. |
| Удалённое приложение возвращается после перезапуска | CLIENTS_JSON применяется однократно, с персистентной отметкой в БД. |

В PostgreSQL хранятся только хеши refresh. Для идемпотентного повтора преемник выводится через HMAC с предыдущим секретным токеном в качестве ключа. Хеш из БД не позволяет вычислить преемника. Повтор за пределами grace window по-прежнему отзывает сессию.

## Почта, Google и защита форм

| Сценарий | Исправление |
| --- | --- |
| Два первых входа создают разные аккаунты для одного адреса | Разрешение личности выполняется транзакционно под блокировками по личности и email; при конфликте повторяется целиком. |
| Одновременные отправки оставляют действующие коды без привязки к попытке | Каждая попытка имеет свой handle (HMAC её id по ключу csrf-cookie браузера) и привязку к браузеру. Переотправка атомарно заменяет код внутри этой попытки. Повторная отправка формы почты из того же браузера (двойное нажатие, «Назад», обновление страницы) во время паузы возвращает экран кода той же попытки без нового письма. |
| Подбор по множеству адресов обходит ограничения | Бюджеты отправки по IP, IP/email и адресу; проверки по IP и атомарный предел пяти проверок на попытку. В production счётчики общие в PostgreSQL. |
| Чужие неверные коды исчерпывают проверки владельца | Без handle и браузерной привязки чужая попытка не изменяется. |
| Google когда-то подтвердил сторонний адрес | При первом входе таким аккаунтом запрашивается код из письма; привязка Google выполняется после подтверждения. Gmail/Workspace проверяются отдельно. |
| Google ID Token повторно предъявляют со своей nonce-cookie | Nonce выпускается сервером, связан с браузером и клиентом, имеет TTL и атомарно погашается; nonce-cookie удалена; выдача ограничена по IP до записи nonce. |
| Соседний поддомен подбрасывает cookie | На HTTPS читаются только `__Host-` имена, POST проверяет Origin/Fetch Metadata и CSRF. |
| Новая форма ломает прежнюю или SSO-cookie истекает раньше серверной сессии | CSRF стабилен между формами, SSO-cookie продлевается при использовании сессии. |
| Сбой Redis отключает ограничения кодов | OTP использует PostgreSQL независимо от Redis. Прочие лимиты при сбое Redis переходят на память процесса. |
| Внешнее приложение тихо получает профиль | `external` требует явного согласия; `prompt=none` не выдаёт ему код. |

Остаётся компромисс защиты почты от спама: посторонний может временно исчерпать бюджет новых входов на адрес (пауза 60 секунд между письмами, 20 в сутки; полная таблица лимитов — в DEPLOY.md). Уже начатая попытка владельца сохраняет свои проверки и повторные отправки. CSRF использует double-submit, `__Host-` и Origin, без отдельного ключа подписи; клиенты без Origin/Fetch Metadata защищаются cookie и токеном формы.

## Установка и эксплуатация

Готовый runtime содержит скомпилированные CLI миграций, ротации и отзыва ключей. Для этих команд TypeScript внутри production-контейнера не требуется. Настройки создаются с уникальными секретами и правами 0600. Сервис требует PostgreSQL и почтового провайдера в production.

Адреса публичного сервиса и модулей проверяются: HTTPS обязателен, HTTP разрешён для localhost. Доверие прокси ограничено указанными адресами. nginx перезаписывает входящий X-Forwarded-For; база и Redis не публикуются наружу.

Восстановление дампа выполняется в пустую БД до запуска приложения, одной транзакцией и с остановкой при ошибке. Порядок приведён в [DEPLOY.md](DEPLOY.md).

## Совместимость

HTTPS-cookie получили префикс `__Host-`, а запечатанный конверт модуля — версию v2 с проверяемым сроком. После обновления прежних приложений пользователям потребуется повторный вход. По локальному HTTP используются отдельные имена без префикса.

При копировании модуля обновите и обработчики примера: Next.js экспортирует GET и POST, Hono регистрирует оба метода. GET выхода показывает подтверждение; выход выполняет POST с проверкой Origin и CSRF.

Активные старые refresh-токены продолжают обновляться. Повтор уже погашенного старого токена со случайным преемником в grace window может потребовать входа заново; сессия при этом не отзывается как украденная.

## Повторный аудит

Второй независимый аудит (шесть агентов трёх разных моделей) нашёл 12 дефектов среднего уровня и 8 мелких; опасных не найдено. Все исправлены.

| Область | Что изменилось |
| --- | --- |
| Адрес в токене | `id_token` и SSO-сессия получают адрес и `email_verified` из базы, а не из ответа провайдера |
| Страница входа | Превышение лимита Google nonce скрывает кнопку Google, вход по почте продолжает работать |
| Согласие | Форма привязана к ожидаемому пользователю и показывает адрес приложения |
| Вход по коду | Лимит вмещает первое письмо и три повторных; исчерпанная попытка не тратит лимит; таймаут отправки письма 10 секунд; отдельное письмо для привязки Google |
| Выход | «Выйти» отзывает сессии этого браузера во всех приложениях (с круга 10 — не трогая другие браузеры и устройства); новый вход гасит прежнюю SSO-сессию |
| Управление приложениями | Коды привязаны к регистрации клиента и к его типу на момент решения о согласии; обмен кода и изменение клиента сериализованы; смена типа отзывает сессии |
| Модуль | Cookie получают суффикс client id; запоздавший refresh не возвращает сессию после выхода или смены пользователя; временный сбой на публичной странице Next.js не выкидывает пользователя |
| Установка | `client.mjs` обращается к сервису внутри контейнера и работает до настройки nginx; миграции под общей блокировкой; `rotate-key` печатает старый kid |

После обновления модуля пользователи приложений один раз входят заново: у cookie новые имена. Смена `type` клиента выкидывает его пользователей.

## Третий аудит

Третий независимый аудит (шесть агентов трёх разных моделей) нашёл один опасный дефект, 15 средних и 14 мелких. Все исправлены, затем ревью исправлений нашло и закрыло ещё девять.

| Область | Что изменилось |
| --- | --- |
| Журнал | Код из письма, адреса, токены и cookie не попадают в журнал: почтовые адаптеры пишут только тип письма и хеш адреса, логгер дополнительно скрывает секретные поля на любой глубине, а объекты ошибок выводит только как тип, сообщение, код ошибки, стек и причину |
| Письма с кодом | Лимит на адрес считает только новые входы; повторная отправка атомарна, письмо уходит до замены кода, код пишется под номером своей отправки и опоздавшее письмо не затирает более новый, при отказе провайдера прежний код работает, при таймауте действует код нового письма; страница отказа показывает время ожидания; отказ провайдера не списывает лимит |
| Страницы входа | Политика клиента проверяется до гашения кода; ошибки в JS-режиме приходят JSON; без `code_challenge` — редирект `invalid_request`; домены на кириллице принимаются; CSRF-cookie не ломает соседнюю вкладку |
| Приложения | Код и попытка входа по почте привязаны к регистрации клиента; refresh идёт под блокировкой клиента |
| Выход и смена аккаунта | Сессии приложений привязаны к цепочке SSO браузера: смена пользователя гасит прежний аккаунт во всех приложениях этого браузера, выход повторяем после сбоя |
| Надёжность | Обрыв соединения с PostgreSQL не роняет процесс; ошибки разбора тела отдают 400/413/415; очистка останавливается при выключении; `/userinfo` с `no-store` и `POST` |
| Модуль | Не-ASCII в `next`; роли берутся из токена, размер cookie проверяется; ленивые обработчики Next.js собираются без `AUTH_*`; попытка входа живёт 60 минут; пауза refresh только при недоступности сервиса |

Миграции 0013 и 0014 применяются поверх данных прежней версии. Попытки входа по коду, начатые до обновления, отклоняются: пользователь один раз начинает вход заново.

## Круги 4–13

Затем десять кругов «аудит → исправление»: в каждом четыре агента (две модели), каждая существенная находка подтверждена прогоном, мелочи в счёт не шли. Цикл остановлен, когда круг 13 не нашёл ни одной существенной ошибки. С круга 8 проверки идут и в настоящих Chromium и WebKit, с круга 12 — глазами ученика, который подключает модуль к новым приложениям строго по README.

| Область | Что изменилось |
| --- | --- |
| Повторная отправка кода | Слоты кодов: код из последнего письма действует, опоздавшее письмо не затирает новый, таймаут провайдера не обходит лимит; двойное нажатие возвращает к той же попытке |
| Лимиты | Пауза 60 секунд между письмами на адрес вместо часового отказа; верный код не тратит лимит проверок; лимиты для класса настраиваются (`CODE_REQUEST_PER_IP_HOURLY`, `CODE_VERIFY_PER_IP_HOURLY`, `GOOGLE_SIGNIN_PER_IP_15MIN`) |
| Журнал | Ошибки сериализуются без адресов и handle; адреса в ответах почтового провайдера заменяются на `[адрес]` |
| Выход и смена аккаунта | Изменения одной цепочки SSO сериализованы, блокировки берутся в одном порядке; cookie привязки браузера (`sso_browser`) находит сессии браузера и после истечения SSO-cookie; «Выйти» гасит только этот браузер; смена пользователя начинает новую цепочку |
| Согласие | Внешнее приложение получает код только после экрана согласия, в том числе сразу после кода из письма |
| Refresh | Формат «семейство.секрет», история погашенных токенов ограничена, повтор удалённого токена по-прежнему отзывает сессию; старые сессии без цепочки доживают срок без продления |
| Модуль | Работает со свежим Next.js 16 (Turbopack, `proxy.ts`, `cacheComponents`) без обходных флагов; «Выйти» работает в Chrome; пример Hono показывает «Повторить» при сбое |
| Эксплуатация | Резервная копия не затирает прежнюю при сбое; миграции под блокировкой; обновление — только с остановкой прежней версии |

## Проверки

CI выполняет TypeScript, тесты сервера и модулей, проверки настоящих PostgreSQL/Redis, сборку production-образа и обоих примеров, синхронность копий модуля и сканирование Git-истории на секреты. Регрессионные сценарии конкурентной ротации и отката транзакции проверяются на отдельной схеме PostgreSQL.

Перед публикацией также проверены HTTP SSR на production-сборке Next.js, CLI внутри Docker и восстановление дампа. Реальная доставка писем и Google-вход требуют настроек владельца установки; автоматические тесты используют подменённые внешние провайдеры и не отправляют письма.

Свойства и ограничения модели безопасности описаны в [SECURITY.md](../SECURITY.md). Проверки не заменяют сопровождение зависимостей и оценку требований конкретного приложения.

# Безопасность

Не публикуйте `.env`, ключи подписи, дампы PostgreSQL и токен Admin API. Пример настроек содержит пустые значения; `scripts/setup.mjs` генерирует отдельные секреты для каждой установки. У приложений должны быть разные `AUTH_COOKIE_SECRET`.

Публичный сервис работает только по HTTPS. HTTP разрешён для localhost при разработке. В nginx переписывайте X-Forwarded-For, а в `TRUST_PROXY` задавайте адреса или CIDR действительно доверенных прокси. В Docker Compose указан gateway выделенной сети; при изменении сети измените и доверенный адрес. Не открывайте порт контейнера напрямую в Интернет.

Сервис использует RS256, Authorization Code с S256 PKCE, короткие access JWT, ротацию refresh и cookie HttpOnly. В PostgreSQL сохраняются хеши одноразовых секретов и refresh-токенов. Повтор уже погашенного refresh-токена позже минуты после погашения считается кражей и отзывает сессию. Очистка удаляет у живой сессии строки refresh-токенов, погашенных больше часа назад, кроме трёх последних. Повтор удалённого токена узнаётся по его первой части, общей для всех токенов сессии, и тоже отзывает сессию. Код из письма, тема и тело письма и открытый адрес получателя в журнал не пишутся: о письме сохраняются только id у почтового провайдера, тип письма и хеш адреса. Логгер дополнительно скрывает поля с заведомо секретными именами (код, адрес, тема, токены, пароли, cookie), а из объектов ошибок оставляет только тип, сообщение, код ошибки, стек и причину. Код стоит в теме письма ради удобства: его видно в уведомлении и его подставляет телефон. Тему и тело письма всё равно видит почтовый провайдер, поэтому защита строится на журнале сервиса. Учётные данные Resend и Google принадлежат владельцу установки.

Токены Google проходят проверку подписи, issuer, audience и срока; nonce привязан к серверной попытке входа. Для автоматической привязки аккаунтов важно, может ли провайдер подтверждать текущее владение email. [Google описывает эту границу для сторонних адресов](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token).

Для защиты от спама новые входы на один адрес идут не чаще одного письма в 60 секунд и не больше 20 в сутки, а все письма ограничены по источнику; итоговые лимиты описаны в DEPLOY.md. Это осознанный компромисс: лимит адреса может занять любой, кто знает адрес. Тогда владелец ждёт паузу до минуты, а если посторонний израсходовал суточный потолок, новый вход в этот адрес закрыт до конца суток. Уже начатая попытка владельца сохраняет свой предел проверок и повторных отправок. Полностью устранить это может только проверка человека (капча), которой в сервисе нет. Выдача Google nonce на странице входа ограничена по IP. OTP и nonce используют общие счётчики PostgreSQL; в dev без БД они локальны процессу.

Вход в браузере хранят две cookie сервиса, обе HttpOnly, с префиксом `__Host-` на HTTPS. SSO-cookie даёт вход без повторного ввода и живёт `SSO_TTL_SECONDS` с последнего захода на страницы входа. Cookie привязки браузера (`sso_browser`) права входа не даёт: в ней случайный секрет, а в базе — только его хеш и цепочка SSO-сессий этого браузера. Она живёт год с последнего входа или захода на страницы входа. По ней «Выйти» и смена аккаунта находят сессии приложений, выданные в этом браузере, даже когда SSO-cookie уже истекла. Сессия приложения продлевается refresh не дальше срока привязки своего браузера, поэтому, пока сессия жива, браузер может её завершить. «Выйти» гасит сессии приложений только своего браузера, по SSO-cookie и по привязке одинаково, и не трогает другие браузеры и устройства пользователя. У цепочки может быть несколько привязок: вкладки, одновременно получившие cookie, получают разные секреты, и действует каждый. Выход по любой из них удаляет все привязки цепочки. Вход другим аккаунтом начинает в браузере новую цепочку с новой привязкой, а прежнюю закрывает: её сессии приложений гаснут, привязки удаляются. Прежние SSO-cookie и копии привязок ведут только в закрытую цепочку, поэтому подсаженная в браузер чужая привязка не даёт её владельцу потом разлогинить вошедшего, даже если тот войдёт со своей прежней SSO-cookie. Тот, кто украл cookie привязки, не может войти, но может разлогинить приложения этого браузера, поэтому храните её как остальные cookie сервиса. Если пользователь сам удалил cookie сервиса, выход в нём завершит только то приложение, из которого он вышел; остальные сессии этого браузера истекут сами.

Внешнему (`external`) приложению профиль выдаётся только после экрана согласия с его названием (client id) и адресом. Сохранённых согласий нет: экран показывается при каждом новом входе, в том числе сразу после кода из письма.

Пользовательские API защищайте на сервере, проверяя сессию или токен для **своего audience**. `/userinfo` принимает access-токены зарегистрированных клиентов; его наличие не даёт права обращаться к чужому API. Сессионные cookie нельзя принимать как единственное доказательство прав после истечения проверенной сессии.

Уже выданный access JWT нельзя мгновенно отозвать при локальной проверке подписи: он действует до своего exp. Ротация или отзыв ключа в текущей реализации требуют перезапуска процесса; клиенты с кэшем JWKS могут обновлять его с задержкой. Перед аварийным отзывом изучите раздел обслуживания в DEPLOY.md.

Не отправляйте действующие ключи, пароли, данные пользователей и полный эксплойт в публичный issue. Для сообщения об уязвимости используйте private vulnerability reporting на вкладке Security репозитория. Если он недоступен, создайте issue только с просьбой о закрытом канале связи, без деталей эксплуатации.

Обновления зависимостей и проверки CI не являются гарантией отсутствия неизвестных ошибок. Перед использованием с чувствительными данными оцените требования своей системы, восстановление из резервной копии и границы доверия между приложениями.

# Безопасность

Не публикуйте `.env`, ключи подписи, дампы PostgreSQL и токен Admin API. Пример настроек содержит пустые значения; `scripts/setup.mjs` генерирует отдельные секреты для каждой установки. У приложений должны быть разные `AUTH_COOKIE_SECRET`.

Публичный сервис работает только по HTTPS. HTTP разрешён для localhost при разработке. В nginx переписывайте X-Forwarded-For, а в `TRUST_PROXY` задавайте адреса или CIDR действительно доверенных прокси. В Docker Compose указан gateway выделенной сети; при изменении сети измените и доверенный адрес. Не открывайте порт контейнера напрямую в Интернет.

Сервис использует RS256, Authorization Code с S256 PKCE, короткие access JWT, ротацию refresh и cookie HttpOnly. В PostgreSQL сохраняются хеши одноразовых секретов и refresh-токенов. Код из письма, тема и тело письма и открытый адрес получателя в журнал не пишутся: о письме сохраняются только id у почтового провайдера, тип письма и хеш адреса. Логгер дополнительно скрывает поля с заведомо секретными именами (код, адрес, тема, токены, пароли, cookie). Код стоит в теме письма ради удобства: его видно в уведомлении и его подставляет телефон. Тему и тело письма всё равно видит почтовый провайдер, поэтому защита строится на журнале сервиса. Учётные данные Resend и Google принадлежат владельцу установки.

Токены Google проходят проверку подписи, issuer, audience и срока; nonce привязан к серверной попытке входа. Для автоматической привязки аккаунтов важно, может ли провайдер подтверждать текущее владение email. [Google описывает эту границу для сторонних адресов](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token).

Для защиты от спама новые входы ограничены по адресу (10 в час, 20 в сутки), а все письма — по источнику; итоговые лимиты описаны в DEPLOY.md. Посторонний способен временно исчерпать бюджет новых входов на чужой адрес. Уже начатая попытка владельца сохраняет свой предел проверок и повторных отправок. Выдача Google nonce на странице входа ограничена по IP. OTP и nonce используют общие счётчики PostgreSQL; в dev без БД они локальны процессу.

Пользовательские API защищайте на сервере, проверяя сессию или токен для **своего audience**. `/userinfo` принимает access-токены зарегистрированных клиентов; его наличие не даёт права обращаться к чужому API. Сессионные cookie нельзя принимать как единственное доказательство прав после истечения проверенной сессии.

Уже выданный access JWT нельзя мгновенно отозвать при локальной проверке подписи: он действует до своего exp. Ротация или отзыв ключа в текущей реализации требуют перезапуска процесса; клиенты с кэшем JWKS могут обновлять его с задержкой. Перед аварийным отзывом изучите раздел обслуживания в DEPLOY.md.

Не отправляйте действующие ключи, пароли, данные пользователей и полный эксплойт в публичный issue. Для сообщения об уязвимости используйте private vulnerability reporting на вкладке Security репозитория. Если он недоступен, создайте issue только с просьбой о закрытом канале связи, без деталей эксплуатации.

Обновления зависимостей и проверки CI не являются гарантией отсутствия неизвестных ошибок. Перед использованием с чувствительными данными оцените требования своей системы, восстановление из резервной копии и границы доверия между приложениями.
